# Troubleshooting: what broke while building this, and why

Every real problem hit while wiring this project end to end: the exact
symptom, the root cause, the fix, and what stops it coming back. Most of
them are in no single vendor doc, because they sit where two platforms meet
(AWS and Salesforce, the board and AWS IoT, the agent and its permissions).

**Rule:** a new problem gets a row here in the same commit as its fix.

The step-by-step "if a step fails" tables stay next to their feature:
[SOP-GROUNDING.md](SOP-GROUNDING.md#if-a-step-fails) and
[DATA-CLOUD.md](DATA-CLOUD.md#if-a-step-fails).

## The board during an OTA update (code review, Nov 11, not fixed yet)

Found by reading firmware 2.6.0 (`CloudAgenticDevice.cpp` `applyFirmware()`, `patient-monitor.ino` `loop()`), not by a failure on a board. Each row says what a fix would be; none is built.

| When | Finding | Root cause | Proposed fix | Status |
| --- | --- | --- | --- | --- |
| Nov 11 | While a build downloads (tens of seconds) the servo stops sweeping: a positional SG90 holds whatever angle it had (a continuous-rotation servo keeps spinning at its last speed). No sensor checks, stored readings or live readings in that time. On the restart the arm goes home and the board forgets the temperature state; it turns again on the first good reading, a few seconds after Wi-Fi is back. Stored readings resume 0 to 30 s after reconnecting, with no backfill. A failed download (no restart) resumes the sweep where the clock says, with nothing lost but that gap | `applyFirmware()` runs inside `_mqtt.loop()` and blocks (`Update.writeStream`) until done, so `loop()` and `driveServo()` never run; the hot/queue state lives only in RAM (`ServoDemand`) | Accept as the cost of an update, or write the download in chunks and call `driveServo()` and the sensor check between them; read the sensor in `setup()` before Wi-Fi so the motor restarts before the network does | Behaviour, documented |
| Nov 11 | A Device Command sent during the download or the restart is lost: the record stays `Sent` with no answer, forever | The board subscribes to `device/<thing>/command` at QoS 0 with a clean session (PubSubClient defaults), so AWS keeps nothing for it, even though device-command publishes at QoS 1; Salesforce has no "no answer" timeout | Subscribe at QoS 1 with `cleanSession=false`, or have Salesforce mark a `Sent` command `Failed` (no answer) after a few minutes; optionally refuse new commands while the Asset is `UPDATING` | Gap |
| Nov 11 | After a build that did not start and the bootloader went back, the board may download and install the same build again, until the job's in-progress timeout (Dev: 10 min for a try, 15 for a fleet release) | During the download nothing is sent on MQTT, and AWS IoT drops a client silent for 1.5x keep-alive (PubSubClient default 15 s, so about 22 s). Then the `IN_PROGRESS "rebooting"` status is lost, and after coming back the board sees `"downloading"` and does not take the `came back on <version>` path | Call `_mqtt.loop()` while downloading (chunked write), or reconnect before reporting "rebooting", and keep "rebooting <jobId>" in NVS so the board knows it on its own | Gap, not yet seen on a board |
| Nov 11 | A new build that starts but then crashes or hangs (in `setup()` or `loop()`) is never rolled back: the board restart-loops on it until someone flashes it over USB | The Arduino core marks a running build valid as soon as it starts, so the bootloader only goes back for a build that cannot start at all; `Update.end(true)` already refuses a corrupt download, which then never boots | Override `verifyRollbackLater()` to return true and call `esp_ota_mark_app_valid_cancel_rollback()` only after Wi-Fi, MQTT and the job's `SUCCEEDED`, with a watchdog that restarts (and so rolls back) if that never happens | Gap |
| Nov 11 | An open live card goes quiet for up to 10 minutes after an OTA restart | Live mode lives in RAM and ends with the restart; the card renews `LIVE` only every 10 minutes (`REFRESH_MS`) | The card asks again when the Asset turns Online, or the board says on connect that live mode is off | Gap |

What does not change: Cases and the alert rule live in Salesforce and AWS, so an open Case stays open through an update; the episode only ends on a stored reading below 29 C. The reading interval is kept in NVS and survives. An internal board is sent the queue's depth again when it comes back Online (`CaseQueueMonitorService.resyncAfterReconnect`).
